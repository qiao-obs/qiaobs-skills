# `trace-feature-chain`：首个偏差链路追踪

> 10 秒定义：当功能只在某个角色、设备、入口、数据状态或发布版本下失败时，沿真实路径找到第一处不匹配，并只修真正的根因层。

- [English guide](trace-feature-chain.md)
- [执行入口](../../skills/trace-feature-chain/SKILL.md)

## 它解决的高代价失败

很多排查从页面最后一句“加载失败”开始，然后直接改文案、加重试、换接口或部署服务器。这样做可能让一个截图看起来好一点，却没有证明原始场景已经恢复。

这个 Skill 专门处理以下故障形态：

- 普通账号正常，特定角色失败；
- 模拟器正常，真机失败；
- 空数据正常，非空数据失败；
- 直接进入正常，从真实入口或再次进入失败；
- 源码已改，但预览、上传或用户仍使用旧产物；
- API 返回正常，但共享契约、运行时或构建产物与预期不一致。

它不把“权限”“可见性”“适用范围”“授权”当成同一个事实，也不把测试通过、构建成功、预览成功、上传成功和用户验收混在一起。

## 何时使用 / 何时不要使用

### 使用它

当你能指出一个真实失败谓词，例如：

> 某授权角色从主界面的真实入口进入公开资料编辑页；只有头像非空且使用真机时失败；预期是进入编辑状态并保留资料。

或者用户明确要求“找第一处不匹配”“做最小安全修复”“确认发布边界”。

### 不要使用它

- 普通 UI 美化或文案改写；
- 单一语法错误，且没有跨层行为差异；
- 一次性翻译或事实问答；
- 没有定位失败链、只要求执行已知部署步骤的任务。

如果已知根因，想要连续完成多个实现和验证阶段，可以把本 Skill 与 `run-autonomous-workpacks` 组合，而不是用它代替执行协议。

## 核心模型

```text
角色 → 业务目标 → 真实入口 → 页面状态 → 权限与身份事实
→ 用户命令 → API → 后端/数据库事实 → 对象存储
→ 共享契约 → 真机运行时 → 构建产物 → 预览/上传版本
→ 再次进入后的结果投影 → 失败恢复与重试
```

链条是推理顺序，不是要求逐个打开所有文件。只有当证据表明某一环可能改变答案时才深入该环。

## 工作流程

### 1. 冻结场景谓词

先记录：

- 角色或账号类别，不记录真实账号标识；
- 业务目标和成功时的可观察结果；
- 设备、运行时、环境和版本；
- 真实入口、页面状态和用户点击；
- 身份、权限、可见性、适用范围和授权事实；
- 空/非空数据、媒体、网络和状态条件；
- 唯一失败表现、预期结果和明确非目标。

若关键字段未知，写出获取证据的最小方式；不要用猜测替代缺失事实。

### 2. 沿链取证

每一环使用同一格式：

```text
Expected: 预期应该是什么
Observed: 实际观察到什么
Evidence: 哪个日志、测试、响应、页面或工具结果支持它
Status: pass | fail | unknown
```

优先检查上游前提，而不是先追最后一个 UI 错误。后续 loading、重试、空白和错误文案可能都是上游偏差的投影。

### 3. 找到第一处偏差

问五个问题：

1. 这个症状出现前，哪些事实必须已经成立？
2. 哪些前提有直接证据，哪些只是默认假设？
3. 哪一环第一次出现 `expected ≠ observed`？
4. 同一代码是否也会被其他角色或非空数据触发？
5.  proposed fix 是否位于症状上游且没有超出范围？

“第一处”指第一个可由证据支持、并足以解释后续症状的逻辑不匹配，不一定是最早执行的文件或最后抛异常的位置。

### 4. 选择最小修复

- 共享契约缺陷：修共享契约，补相同数据形状的回归；
- 权限/策略缺陷：修策略评估，不用界面特判遮掩；
- 前端运行时缺陷：改兼容实现，验证目标运行时，不重部署无关后端；
- 后端/数据缺陷：修生产层并先证明返回形状，再改消费者；
- 构建/发布缺陷：重新生成或发布正确产物，不把源码修改当作交付。

不使用账号 ID 特判、猜测性 fallback、无关重构和破坏性操作。

### 5. 分层验证并复测原场景

验证顺序通常是：

1. 保留原始失败条件的最窄回归；
2. 仓库静态检查和单元测试；
3. 依赖生成和构建产物；
4. 目标运行时或预览；
5. 上传、发布和用户确认（如果在范围内）；
6. 从原入口重新进入，并测试重试/恢复。

每一步只证明自己的层。`source changed` 不等于 `released`，`upload succeeded` 也不等于用户已经重新进入并验收。

## 输入与输出

### 需要的输入

- 角色类别、设备/运行时和环境；
- 真实入口与操作顺序；
- 最小失败数据条件；
- 预期结果与唯一失败表现；
- 允许修改的范围和明确不应触碰的边界；
- 可安全访问的日志、响应、测试、构建或发布证据。

### 输出格式

```text
Scenario predicate:
Scope and non-goals:
Chain status:
First mismatch:
Root cause and affected layer:
Minimal safe fix:
Evidence and verification:
Release boundary:
Remaining risks or user checks:
```

## 完整匿名案例

一个匿名校园信息小程序中，有权限的运营角色可以在模拟器编辑公开资料；真机只在账号已有头像或背景图时失败。后端接口返回正常，页面却显示加载失败。

普通处理方式可能是：

- 给这个角色加特殊分支；
- 把错误文案改成“网络异常”；
- 增加无限重试；
- 重新部署后端以“确保生效”。

使用本 Skill 后：

1. 固定“真机 + 非空媒体 + 真实入口”的原始谓词；
2. 证明权限和 API 返回正常；
3. 发现共享图片契约依赖目标运行时不保证存在的浏览器 API；
4. 将第一处偏差定位在共享契约/运行时边界；
5. 修共享校验逻辑，补真实签名媒体地址回归；
6. 分别检查生成依赖、真机预览和上传版本。

该案例记录过 1 个共享源文件、1 个回归测试文件和 31 项定向检查通过。这是单个匿名案例记录，不是普遍性能指标。

## 三个可复制提示词

### 提示词 1：跨层故障

> 某授权角色从真实入口进入页面时失败，但另一个角色和模拟器正常。请先冻结角色、设备、入口、数据条件和预期结果，沿页面→权限→API→数据→契约→运行时→构建→发布链找第一处偏差，不要先改错误文案。

### 提示词 2：构建/发布边界

> 源码中的修复已经通过测试，但手机仍表现旧行为。请分别核对生成依赖、构建产物、预览/上传版本和再次进入结果；不要把“文件已改”报告成“用户已拿到修复”。

### 提示词 3：权限与数据差异

> 只有非空媒体数据触发失败。请区分身份、权限、可见性、适用范围和授权事实，再比较空/非空数据和共享代码路径；若是共享契约缺陷，不要写账号特判。

## 典型输出片段

```text
First mismatch:
- Link: shared contract → target runtime
- Expected: media URL validation works on the real device
- Observed: helper calls a browser-only constructor when media is non-empty
- Evidence: API shape test passes; device error appears only with media; shared helper is common to both roles

Minimal safe fix:
- Change the shared helper and add a regression for the original media condition
- Leave backend, permissions, and unrelated pages untouched

Release boundary:
- Local regression: pass
- Build artifact: unknown until regenerated
- Device preview/upload: unknown
- User acceptance: unknown
```

## 反模式和失败条件

- 用更容易的账号、空数据或模拟器替代原条件；
- 只看最后的错误文案；
- 把 HTTP 200 当成页面成功；
- 把可进入页面当成完整功能成功；
- 修共享问题时写账号特判；
- 测试通过后跳过构建/预览/发布层；
- 未授权就部署、上传、发消息或删除数据；
- 为了“闭环”填补 `unknown`。

遇到无法安全判断的关键事实，应先收集最小证据；遇到未授权外部动作，应标记边界而不是推断授权。

## FAQ

### 为什么不直接从错误文案开始？

因为错误文案通常是链条后段的投影。先固定场景并沿上游取证，才能分辨页面状态、权限、API、契约和运行时的责任。

### 为什么强调非空数据？

空数据经常绕过解析、渲染或对象存储路径。只有非空条件才可能触发实际失败分支。

### 测试通过后为什么还要预览和上传？

测试证明测试 harness 覆盖的行为；预览、上传和用户验收各自证明不同交付层。

### 什么时候应该和 `run-autonomous-workpacks` 组合？

当根因定位之后，任务还包含实现、测试、构建、文档和收尾，并且这些动作已经明确授权时。
