# `run-autonomous-workpacks`：完成有界、多阶段工作

> 10 秒定义：当多阶段任务已经获得授权，把它转成范围清楚、依赖明确、可恢复、可验证的工作包，并如实收口。

- [English guide](run-autonomous-workpacks.md)
- [执行入口](../../skills/run-autonomous-workpacks/SKILL.md)

## 这个 Skill 解决什么问题

大型任务常常同时包含现状审计、实现、测试、文档、构建和 Git 收尾。没有工作结构时，Agent 可能忘记原始范围、重复失败命令、把无关改动混入 diff，或把本地通过误写成用户已经拿到结果。

`run-autonomous-workpacks` 提供一套紧凑的执行方法：

1. 建立任务契约；
2. 拆成可以独立验证的工作包；
3. 按依赖和副作用排序；
4. 在授权边界内执行安全工作；
5. 根据失败原因进行有限修正和重试；
6. 验证整体结果并记录真实状态。

该 Skill 只规定工作组织、执行边界和验证方法，不改变 Codex 原生的对话、进度展示或子代理体验。

## 什么时候使用

适用于用户已经给出足够目标、范围和授权，且任务包含多个相互连接的动作，例如：

- 检查仓库、实现一个有界改动、运行测试、更新文档并准备评审；
- 迁移数据结构，同时准备回滚说明、夹具、验证和收口记录；
- 准备发布包，但把公开发布或生产动作明确分离；
- 修复跨文件问题，并为每个阶段定义输入和完成条件。

不适用于：

- 一行改写、翻译、事实查询或孤立语法解释；
- 明确禁止修改的分析-only 或诊断-only 请求；
- 下一次修改依赖关键事实，而该事实尚未取得的任务；
- 没有明确授权的付费、删除、生产、发布、账号变更或其他高影响动作。

## 输入与输出

### 输入

- 目标和验收条件；
- 允许与禁止的路径或系统；
- 权威文件、记录、测试和约束；
- 明确允许的外部动作，以及必须保持分离的动作；
- 必须保留的现有用户修改。

### 输出

- 任务契约；
- 工作包卡片和依赖板；
- 每个工作包的修改、检查、失败、重试和证据；
- 明确未触碰的范围；
- 带有 `verified`、`unknown`、`skipped`、`failed` 或 `blocked` 的分层验证；
- `COMPLETE`、`PARTIAL` 或 `BLOCKED` 的真实收口状态。

## 工作包方法

### 1. 写任务契约

在修改前记录目标、范围、非目标、副作用预算、权威输入、验收条件和停止条件。成功登录只能证明有访问能力，不能推导所有外部动作都已获准。

### 2. 定义工作包卡片

每张卡片都要有一个目标、准确写入范围、明确不触碰的路径、输入、依赖、风险、完成条件、检查、恢复路径、状态和证据。文档、实现、安装和发布范围应保持分离。

### 3. 按依赖执行

先发现基线；再准备必要的夹具或临时目录；然后做最小一致改动；先验证目标行为，再运行仓库级检查；只有本地证据充分且请求明确授权时才执行外部动作。

### 4. 从失败中恢复

保留命令和退出码，判断第一条关键错误属于内容、环境、依赖、权限还是外部状态；只做一次有依据的修正；重新运行最小决定性检查。如果有限尝试后仍无法解释，就保留 `PARTIAL` 或 `BLOCKED`，不要把猜测写成通过。

### 5. 用分层证据收口

源代码 diff 只能证明预期文件发生变化；测试只能证明覆盖的测试环境；构建只能证明生成了产物；预览、上传、Release 和用户报告分别证明各自层次。收口时不能把这些结论互相替代。

## 一个匿名案例

一次公开 Skill 仓库精修包含：基线检查、入口和 references 调整、双语说明页、图像资产、确定性验证、隔离安装、CI、PR、合并和 Release。安全拆分为：

- WP-01：检查当前分支、远程、Release 和工作树；
- WP-02：精修 Skill 入口和 references；
- WP-03：生成并检查图像和 README 渲染；
- WP-04：运行静态、单元、链接、隐私和安装检查；
- WP-05：只有本地证据通过后才进入评审和发布动作。

如果外部权限不可用，前四个工作包仍然有价值，第五个工作包明确保持阻塞；本地证据不会被写成已经发布。

## 三个可复制提示词

### 提示词 1：已授权实施

> 请在已授权范围内连续完成审计、实现、回归测试、文档和收尾。保留现有修改，只写入指定范围，不使用破坏性命令，并把本地验证与外部交付分开记录。

### 提示词 2：诊断-only边界

> 只做诊断，不修改、不部署、不上传。请建立证据导向的工作包记录，把修改工作标记为未授权，并指出以后实施所需的最小关键事实。

### 提示词 3：有限重试

> 某个验证命令失败。请保留命令和退出码，判断失败类型，只做一次有依据的修正后重试，并按照证据把结果记为 `verified`、`unknown`、`partial` 或 `blocked`。

## 典型收口记录

```text
Outcome: PARTIAL
Completed workpacks:
- WP-01 基线：verified
- WP-02 范围内实施：verified
- WP-03 确定性检查：verified
Changed artifacts:
- README.md：默认首页叙事
- skills/<name>/SKILL.md：渐进式披露
Verification:
- 仓库验证：PASS
- 隔离安装：PASS
- 远程合并：SKIPPED — 权限拒绝
Untouched scope:
- 生产系统和无关用户修改
Open blockers:
- 合并前需要维护者完成一个动作
```

## 反模式和失败条件

- 把用户的“只分析”当成修改授权；
- 创建没有完成条件或准确写入范围的工作包；
- 没有改变诊断就重复失败命令；
- 从本地测试或成功登录推导发布完成；
- 独立检查共享同一临时目录；
- 重置或清理未知的用户文件；
- 必需证据层仍未知却声明 `COMPLETE`。

## 如何组合

如果主要问题是定位跨层偏差，优先使用 `trace-feature-chain`；如果主要问题是基于证据的学习、计划、评估或判断更新，优先使用 `reason-from-reality`。只有授权执行部分需要连续工作包时，才加入本 Skill，不要让执行规划替代主要推理方法。

## FAQ

### 这个 Skill 会授予发布权限吗？

不会。它只组织已经获得授权的工作。发布、生产变更、付费动作、删除、账号变更和外部消息都需要各自明确授权。

### 诊断-only 请求能使用它吗？

可以用它整理只读证据，但必须把修改工作排除在范围外，不能推导实施许可。

### `PARTIAL` 和 `BLOCKED` 有什么区别？

`PARTIAL` 表示有用工作已经验证，但还存在一个有界缺口；`BLOCKED` 表示下一项必需动作无法在没有用户输入或外部状态变化的情况下安全完成。

### 为什么要把构建、预览、上传和 Release 分开？

每一层证明的事实不同。分开记录可以避免把本地源代码或测试结果写成用户实际能够收到的结果。

### 它会改变 Codex 原生体验吗？

不会。它定义工作拆分和证据记录；Codex 仍然使用原生的交互和展示方式。
