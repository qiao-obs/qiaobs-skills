# `run-autonomous-workpacks`：少打扰、不断联的可见自治协议

> 10 秒定义：当任务已经获得明确授权，并且包含多个相邻阶段时，把它拆成有边界、可验证、可重试的工作包；主动汇报阶段状态，但不要求用户逐步确认。

- [English guide](run-autonomous-workpacks.md)
- [执行入口](../../skills/run-autonomous-workpacks/SKILL.md)

## 可见自治协议

方法名：**Observable Autonomy Protocol / 可见自治协议**。

```text
低打扰，不低可见。
高自治，不越授权。
持续执行，不静默失联。
进度汇报，不索取确认。
真正阻塞，才请求用户。
```

低交互降低的是用户必须提供的输入、交接和逐步确认，不降低用户对当前阶段、已完成证据、未验证项、风险和发布边界的知情。

- `CHECKPOINT`：信息性进度更新，发出后继续，不等待回复；
- `GATE`：真实授权或输入门，只在登录/MFA、权限拒绝、未授权高影响动作、关键事实缺失或无法安全验证时等待。

默认模式是 `observable`；只有用户明确要求“静默执行”才进入 `quiet`。预计超过两分钟的任务要在启动、阶段转换、重要失败/改道和没有自然里程碑时的有界心跳汇报新信息；不逐命令直播，也不发空泛“还在处理”。

启动示例：

```text
CHECKPOINT（不等待回复）：已完成范围确认；正在审计基线；静态验证尚未运行；当前未提交。我会继续，下一次在基线冻结或进入实施时汇报。
```
## 它解决的高代价失败

“请尽量一次做完”不应该导致 Agent 每做一步都回来问“继续吗”；但“低交互”也不应该变成无限扩大权限。这个 Skill 解决的是**执行组织问题**：如何在不猜测关键事实、不越过授权边界的前提下，把检查、实现、测试、文档和收尾串成一个能复核的过程。

它特别适合：

- 已授权的跨文件实现；
- 审计→设计→修改→测试→文档→收尾；
- 已知根因后的大范围但有边界的修复；
- 需要保存已有修改、减少交接、保持可见并记录失败恢复的连续任务。

## 何时使用 / 何时不要使用

### 使用它

用户已经明确了目标、范围、非目标和允许的副作用，例如：

> 在当前仓库中完成这次 v0.2 精修：保留历史，只改本仓库，完成验证后按提示词创建 PR、合并和发布；遇到登录/MFA 或权限拒绝才停。

### 不要使用它

- 用户只要求“分析”“审查”“给方案”或明确说“不修改”；
- 关键事实缺失会改变目标、身份、授权或高影响动作；
- 下一步是未授权的生产部署、付费、删除、发消息、上传或不可逆动作；
- 单一小任务没有有意义的阶段、依赖或收尾。

低打扰不能把“已登录”推导成“已获准发布”，也不能把外部工具能做的事当成用户已经授权的事。

## 四条不可混淆的边界

```text
低交互 ≠ 不汇报
高自治 ≠ 扩大授权
连续执行 ≠ 忽略失败
少提问 ≠ 猜测关键事实
```

日常、可逆、在范围内的检查和修改可以连续推进；登录、MFA、权限拒绝、人工审批、付费、生产变更、破坏性动作和关键事实缺失必须保留真实边界。

## 工作包生命周期

```text
任务契约 → 可验证工作包 → 按依赖推进
→ 局部失败诊断/重试 → 整体验证 → COMPLETE/PARTIAL/BLOCKED
```

### 1. 写任务契约

在第一次修改前固定：

- **目标：** 最终要观察到什么；
- **范围：** 哪些文件、系统、产物和外部动作可以改变；
- **非目标：** 明确不做什么；
- **输入：** 哪些提示词、文件、记录和工具结果是权威来源；
- **验收：** 每一项如何被直接观察；
- **副作用预算：** 允许、需要证据后再做、禁止；
- **停止条件：** `USER_ONLY`、`EXTERNAL_WAIT`、`UNAUTHORIZED_HIGH_IMPACT`、`MISSING_FACT`、`FAILURE_UNRESOLVED`。

### 2. 设计工作包

每个工作包只承担一个独立结果，并记录：

```text
ID / 名称 / 目标 / 输入 / 允许写入范围
依赖 / 风险 / 完成条件 / 检查 / 恢复方式 / 状态 / 证据
```

好的名称是“审计当前流程”“补齐精简入口”“运行安装冒烟”“检查发布门禁”，而不是“改进项目”。尽量让不同工作包写入范围不重叠。

### 3. 按依赖推进

推荐四个波次：

1. **Discover：** 读取约束、审计基线、确认不触碰的范围；
2. **Prepare：** 创建分支和受控目录，准备输入，不提前修改行为；
3. **Implement：** 按最小可验证结果完成内容、代码或资产；
4. **Verify/Close：** 先窄检查，再全量检查，最后审查 diff 和外部结果。

不共享可变状态的检查可以并行；会改变安装目录、浏览器状态或外部资源的检查要使用隔离临时目录。

### 4. 处理局部失败

例行命令失败不等于立即停下，也不等于盲目重复。使用：

1. 保存完整输出和退出码；
2. 将失败分类为内容、环境、依赖、权限或外部状态；
3. 只做一个有诊断依据的修正；
4. 重新运行最小决定性检查；
5. 只有完成条件被证据支持后，才把工作包标记为 `verified`。

网络超时可对幂等请求进行一次安全重试；认证或权限失败不是重试邀请；模糊的产品决策不是环境故障。

## 输入与输出

### 需要的输入

- 用户任务、附件提示词和项目约束；
- 当前仓库/系统状态；
- 允许的写入范围和外部副作用；
- 每个阶段的直接验收方式；
- 用户只需在何种情况介入的定义。

### 输出内容

- 任务契约；
- 工作包执行板和依赖关系；
- 每个包的修改、检查、失败与重试证据；
- 完成、跳过、未知和阻塞项；
- 变更文件和明确未触碰的范围；
- `COMPLETE`、`PARTIAL` 或 `BLOCKED` 的真实收口状态。

最终报告最少应包含：

```text
Outcome: COMPLETE | PARTIAL | BLOCKED
Completed workpacks:
Changed artifacts:
Verification:
Assumptions:
Open blockers or follow-ups:
```

## 完整匿名案例

一个公开 Skill 仓库精修任务包含：现状审计、内容结构调整、视觉资产、双语说明页、验证器、安装冒烟、GitHub Actions、PR、合并和 Release。

普通处理方式可能是边写边问：

- 要不要换配色？
- 要不要现在跑测试？
- 要不要创建分支？
- 要不要开 PR？

使用本 Skill 后，先从任务契约中提取提示词已经给出的默认决策，然后把安全工作分成独立包：

- WP-01：确认当前 `main`、远程、Release 和工作树；
- WP-02：在功能分支精修 Skill 入口、references 和双语文档；
- WP-03：生成和检查图像、元数据与 README 渲染；
- WP-04：运行静态、单元、链接、隐私和安装检查；
- WP-05：只在本地门禁通过后进入 PR、CI、合并和 Release。

如果 GitHub 权限被拒绝，WP-01～WP-04 仍然可以完成；WP-05 标记 `EXTERNAL_WAIT`，不会把本地结果冒充成发布结果。

## 三个可复制提示词

### 提示词 1：低交互修复

> 请在当前授权范围内连续完成审计、实现、回归测试、文档和收尾。保留用户修改，不使用 `git reset --hard` 或 `git checkout --`，只有遇到登录/MFA、权限拒绝、未授权高影响动作或关键事实缺失才停。

### 提示词 2：诊断-only边界

> 只做诊断，不修改、不部署、不上传。请建立工作包和证据矩阵，标记哪些动作因授权边界必须跳过，不要把“尽量一次完成”推断成实施许可。

### 提示词 3：失败重试

> 某个验证命令失败。请保留失败证据，判断是内容、环境、依赖、权限还是外部状态问题，只做一个有依据的修正后重试；如果仍无法证明完成条件，报告 `PARTIAL` 或 `BLOCKED`。

## 典型输出片段

```text
Outcome: PARTIAL
Completed workpacks:
- WP-01 baseline audit: verified
- WP-02 scoped implementation: verified
- WP-03 deterministic tests: verified
Changed artifacts:
- README.md: default narrative
- skills/<name>/SKILL.md: progressive disclosure
Verification:
- static validation: PASS
- install smoke: PASS
- remote merge: SKIPPED — permission denied
Assumptions:
- no material assumptions
Open blockers or follow-ups:
- one authorized repository maintainer action is required before merge
```

## 反模式和失败条件

- 把用户的“只分析”当成修改授权；
- 每一步都询问，导致已授权工作无法连续推进；
- 为了少打断而跳过验证或隐藏失败；
- 用成功登录推断发布授权；
- 把一个工作包做成没有完成条件的愿望清单；
- 独立检查共享同一临时安装目录；
- 在工作树混合修改时覆盖或清理用户文件；
- 没有直接证据却把状态写成 `COMPLETE`。

## FAQ

### 低交互到底什么时候可以继续？

当动作可逆、在明确范围内、输入足够且不会产生未授权高影响副作用时。读取、搜索、局部修改、测试、构建和隔离冒烟通常属于此类。

### 什么时候必须停下？

用户必须亲自完成登录/MFA，外部服务拒绝权限，动作涉及未授权生产/付费/删除/发布，关键事实缺失会改变安全决策，或有界重试后仍无法解释失败。

### `PARTIAL` 和 `BLOCKED` 有什么区别？

`PARTIAL` 表示安全且有用的工作已验证，但有一个已知、受限、非必要或外部不可观察的缺口；`BLOCKED` 表示下一项必需动作无法在没有用户输入或外部状态变化的情况下安全完成。

### 为什么还要回报进度？

因为少交接不是少透明。里程碑回报让用户知道当前改了什么、验证到哪一层、下一步是否会产生外部副作用。
